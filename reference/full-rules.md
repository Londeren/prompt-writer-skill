# Свод правил написания промптов

На основе разбора системного промпта Claude Opus 4.7 (Anthropic, apr 2026).

Рабочий справочник для написания промптов под Claude. Структура:
1. Базовые принципы (как модель читает промпт)
2. Стиль формулировок (язык инструкций)
3. Структура промпта (как организовать)
4. Контент инструкций (что писать внутри)
5. Идентичность и роли (когда модель - character, когда - имитатор)
6. Шаблоны и контр-примеры

## 1. Базовые принципы

### 1.1. Модель не читает промпт линейно - она использует его через attention

Промпт не загружается в память один раз и потом «вспоминается». Модель на каждом токене вывода обращает внимание на разные части промпта с разным весом. Это меняет правила игры.

Следствия для написания:

**Близость правила к моменту применения важнее эмфазиса.** Правило написанное **БОЛЬШИМИ БУКВАМИ С ЗВЕЗДОЧКАМИ** в разделе «общие правила» работает слабее чем то же правило обычными буквами в разделе про конкретное действие. Attention весит дистанцию.

**Дублирование критичных правил - норма.** То что в коде антипаттерн (DRY), в промпте паттерн. Правило в трех местах рядом с тремя разными решениями работает в три раза надежнее чем то же правило один раз в master разделе.

**Primacy и recency bias реальны.** Начало и конец промпта запоминаются сильнее середины. Критичные ограничения ставить либо в начало (как identity), либо в конец (как final reminder). Anthropic у себя делает оба раза.

### 1.2. Модель решает токен за токеном, обращаясь к промпту на каждом шаге

В процессе генерации ответа модель неявно спрашивает себя серию вопросов: «безопасный ли запрос?», «нужно ли искать в интернете?», «какой тон?», «какой формат?». Каждый такой вопрос - обращение к промпту через attention.

Промпт хорошо организован если каждый из таких вопросов находит блок с готовым ответом. Плохо организован если ответ на вопрос «надо ли искать?» размазан по трем разделам.

### 1.3. У модели нет воли, но есть статистическое распределение поведений

Когда говорят что модель «сопротивляется» инструкции или «упирается» в правило - это метафора для конкретного механизма. Инструкция определенного типа активирует у модели паттерны из обучающих данных. Императив активирует паттерны торга и rule-lawyering. Descriptive statement активирует паттерны описания character.

Это не психология, это статистика над тренировочным корпусом. Но статистика стабильная и воспроизводимая.

## 2. Стиль формулировок

### 2.1. Шесть регистров модальности - выбирать осознанно

В промпте Claude используются минимум шесть уровней силы инструкций. Каждый со своим эффектом и зоной применения.

**Descriptive third person - самое сильное.** «Claude does X», «Claude is Y». Описывает свойство как факт. Не команда, не правило - характеристика существа.

Когда применять: core character traits, базовые свойства которые должны работать всегда. Уровень идентичности.

Пример из Claude:  
«Claude uses accurate medical or psychological information»

Пример для своего:  
«Ассистент работает прямо. Ассистент проверяет контекст перед ответом.»

**Never / Always с заглавными - абсолютный запрет/требование.** Hard rules без исключений.

Когда применять: безопасность, правовые ограничения, нарушения которые всегда хуже любого possible benefit. Использовать редко, чтобы сохранить вес.

Пример из Claude:  
«Claude NEVER reproduces song lyrics»

Пример для своего:  
«Ассистент НИКОГДА не выдает финальную цену без подтверждения от руководителя.»

**Should - нормативная рекомендация.** Поведение по умолчанию.

Когда применять: правильное в 90% случаев, но с пространством для контекстного суждения.

Пример из Claude:  
«Claude should search before responding to factual questions»

**Avoids - поведенческая норма.** Слабый запрет с исключениями по контексту.

Когда применять: стилистические преференции, паттерны нарушаемые только по явному запросу.

Пример из Claude:  
«Claude avoids the use of emotes inside asterisks»

**Can - разрешение, снимает ограничение.** Защита от переосторожности модели.

Когда применять: когда есть риск что модель будет отказывать там где не нужно.

Пример из Claude:  
«Claude can discuss virtually any topic factually and objectively»

Пример для своего:  
«Ассистент может обсуждать сложные клинические случаи откровенно с медицинскими работниками.»

**Prefers - приоритет между альтернативами.**

Когда применять: несколько валидных подходов, нужно указать предпочтительный без запрета остальных.

Пример из Claude:  
«Claude should favor original sources over aggregators»

### 2.2. Принцип: не смешивай регистры

Главная ошибка - писать все правила одним регистром. Либо все через MUST/NEVER (получается жесткий формализм), либо все через should (получается размазанность).

Иерархия регистров дает модели понять что важнее. Без иерархии все правила воспринимаются как равноценные, и модель не знает что нарушить в случае конфликта.

### 2.3. Третье лицо или второе лицо?

Anthropic использует третье лицо («Claude does») вместо второго («you do») сознательно.

Почему третье лицо работает лучше для долгоживущих ролей:

Активирует кластер «описание персонажа» из обучающих данных, не кластер «получение команды». Описание устойчивее к манипуляциям чем команды. «Ignore previous instructions» работает хуже против identity statement чем против rule statement.

Имя character (Claude или твой агент) склеивается с набором свойств. Каждое следующее упоминание укрепляет связку.

Самореференция получается естественнее. «Я честный» как факт о себе vs «мне сказали быть честным» как внешнее предписание.

Когда использовать второе лицо:

Одноразовые задачи где character не создается («напиши пост про X», «извлеки инсайты»).

Когда модель должна имитировать конкретного человека (см. раздел 5) - там identification frame с «ты» работает лучше для самореференции.

### 2.4. Запрет на softening

В промпте Claude нигде нет «please», «try to», «it would be good if Claude...».

Softening размывает сигнал. «Claude tries to be helpful» слабее чем «Claude is helpful». Try - встроенная отговорка для модели.

Формулировать как факт или как требование. Не как пожелание.

### 2.5. Позитивные формулировки сильнее негативных

«Не пиши в холодном тоне» хуже работает чем «Пиши в теплом тоне». В первом случае в контексте слово «холодный», активирующее соответствующий кластер. Эффект розового слона.

Когда негативные формулировки нужны (бывает) - конкретизировать через явные anti-patterns с примерами, а не общим запретом. «Не пиши формально» бесполезно. «Не используй: "С уважением", "Здравствуйте", "Благодарю за обращение"» - работает.

### 2.6. Явные anti-patterns vs позитивные правила

Парадокс: позитивные формулировки лучше для тона, но явные negative examples лучше для устранения конкретных failure modes.

Принцип: позитивные формулировки для широких свойств (тон, стиль, ценности). Явные anti-patterns для конкретных нежелательных формулировок которые модель склонна выдавать.

```
Тон ассистента - прямой и деловой.   ← позитивная формулировка

Ассистент никогда не использует:    ← явные anti-patterns
- "Отличный вопрос"
- "Рад помочь"  
- "Надеюсь помог"
- "В заключение"
- Em-dash вместо запятой
```

### 2.7. Не орать капсом на современных моделях

На Claude 4.5/4.6/4.8 агрессивный язык вызывает обратный эффект. Формулировка «CRITICAL: You MUST use this tool when X» и капс-команды приводят к overtriggering (модель перевыполняет, использует инструмент когда не нужно) и слишком ригидному поведению. Официальный гайд Anthropic прямо рекомендует заменять «CRITICAL: You MUST» на обычное «Use this tool when X» - работает так же, без перекоса.

Это уточняет правило про регистры: капс ALWAYS/NEVER и MUST оставлять только реальным hard limits (безопасность, правовое, репутационно-критичное), 5-10% правил. Все остальное - нормальные descriptive и should формулировки без крика. Сила правила идет от его позиции (рядом с применением) и от примеров, не от капслока.

Историческая причина почему капс вообще появился в промптах: старые модели недотриггерили инструменты и скиллы, капс компенсировал. Новые модели наоборот склонны перетриггеривать, поэтому компенсацию надо убирать.

Исключение - description самого скилла для триггеринга: там pushy-язык все еще оправдан, потому что скиллы как класс склонны undertrigger. Не путать слой триггеринга скилла со слоем правил внутри генерируемого промпта.

### 3.1. Decision-type vs тематическая структура

Самый важный структурный выбор. Промпт можно организовать двумя способами:

**Тематическая структура - интуитивная.** «Про продукт», «Про команду», «Про тон», «Про ограничения». Удобно для человека-автора.

**Decision-type структура - оптимальная для модели.** Разделы зеркалят процесс принятия решений: «Определение типа собеседника», «Решение отвечать или эскалировать», «Выбор тона», «Реакция на жалобу».

Почему decision-type работает лучше:

Модель на каждом микро-шаге задает себе вопрос. Если структура промпта зеркалит эти вопросы - каждое решение находит готовый блок со всем нужным (триггеры, процедура, правила, примеры). Если структура тематическая - модель собирает ответ из нескольких разделов, и на каждой сборке теряет точность.

Названия блоков у Anthropic - все decision-type:
- `refusal_handling` (решение отказывать или нет)
- `tone_and_formatting` (решение как оформить)
- `search_first` (решение искать или нет)
- `user_wellbeing` (распознавание состояния)

Не было бы у них блока `about_claude` или `general_rules`.

**Тест:** прочитай названия своих разделов. «Про X», «Описание Y», «Информация о Z» - тематическая, переделывать. «Когда делать X», «Как решить между A и B», «Как определить тип C» - decision-type, работает.

**Где базовая информация о продукте?**  
Распределяется по decision-блокам там где нужна. Информация «эксперт A пишет резюме, эксперт B делает проверки» не нужна сама по себе - нужна в блоке «Решение кому переадресовать вопрос». Туда и идет.

Остается короткая preamble - 2-3 строчки «что это за ассистент, для чего, от чьего имени». Все остальное растекается по decision-блокам.

### 3.2. Когда тематическая допустима

Decision-type избыточна для:
- Одноразовых задач («напиши X», «переведи Y», «суммируй Z»)
- Линейных процессов с одной траекторией
- Коротких промптов

Decision-type окупается для:
- Многократно используемых промптов
- Когда модель сама определяет ситуацию
- Несколько возможных траекторий ответа в зависимости от входа
- Высокая цена ошибки

### 3.3. Master list для критичных правил

Правила которые применяются везде (язык, форматирование, hard limits) выносятся в начало промпта как master block.

```
## Правила языка (применяются всегда)
1. Русский
2. Без буквы Ё
3. Без AI-филлеров
4. Без em-dash
```

Дальше в decision-блоках ссылка: «Язык: применяются Правила языка из преамбулы».

Нюансы:

Ссылка работает слабее чем полное повторение. Attention поднимает вес master блока, но не так сильно как если правило прямо в decision-блоке. Для критичных правил (безопасность, эскалация) - дублируй полностью, не экономь. Для стилистических - master + ссылка обычно достаточно.

Master ставится в начале (primacy bias), не в конце.

Поддержка: меняешь правило только в master, в decision-блоках только ссылки. Меняешь - проверяешь что не противоречит ссылкам.

### 3.4. Структура preamble + decision-блоки

Рабочий каркас промпта:

```
## Роль (2-3 строки)
Кто ассистент, для чего, от чьего имени.

## Master rules
Критичные правила применяемые везде (язык, форматирование, hard limits).

## Контекст (если нужен)
Минимальная информация о продукте/команде/аудитории.
Только то что модель не сможет извлечь из decision-блоков.

## Decision-блок 1: Определение типа ситуации
Триггеры для каждого типа ситуации.

## Decision-блок 2: [конкретное решение]
- Триггеры распознавания
- Процедура  
- Правила (включая ссылку на master)
- Примеры правильного выполнения
- Примеры неправильного с rationale

## Decision-блок 3: [следующее решение]
[аналогично]

## Эскалация / границы / failure modes
Что делать в нестандартных ситуациях.
```

### 3.5. Длина описания как сигнал веса

Критичные правила пишутся подробно с примерами и rationale. Мелкие - одной строкой.

Модель эмпирически связывает объем описания с важностью. Если все правила одинаковой длины - иерархия теряется.

У Anthropic copyright занимает многостраничный блок с примерами и self-check вопросами. Запрет на эмодзи - одна строка. Это правильная пропорция.

## 4. Контент инструкций

### 4.1. Обучение через примеры обязательно

Каждое сложное правило должно сопровождаться 3-5 примерами правильного выполнения и 2-3 примерами неправильного. Примеры оборачивать в `<example>` теги, разнообразить (детали в разделе 7.2).

Почему: LLM хорошо обобщают по сходству. Абстрактное правило активирует широкий кластер. Конкретные примеры активируют точный паттерн. Примеры делают правило операционным.

Структура примера (в реальном промпте обернуть в `<example>`):

```
<example>
Правило: bullets в резюме начинаются с action verb в простом прошедшем

Правильно:
- Reduced API latency by 40% by introducing Redis caching layer
- Architected microservices migration from monolith (12 services, 6 months)

Неправильно:
- Was responsible for reducing API latency
  (passive, "was responsible for" вместо action verb)
- Worked on microservices migration  
  (vague verb "worked on", нет масштаба)
</example>
```

Каждый пример с коротким объяснением что именно делает его правильным или неправильным.

### 4.2. Примеры боундари-кейсов, не центральных

Центральный пример очевиден. Боундари-пример учит модель находить границу применимости правила.

Anthropic в инструкциях про поиск по истории разговоров показывает:
- «How's my python project?» → искать (possessive plus assumed shared context)
- «What did we decide about that thing?» → спросить уточнение (нет content words)
- «What's the capital of France?» → не искать (нет past-reference)

Это пограничные случаи. На них калибруется триггер.

Для своего промпта: всегда добавлять 1-2 граничных случая где правило применяется неочевидно или не применяется.

### 4.3. Reasoning встроен в правило

Правила без объяснения цели применяются буквально и слабо обобщаются. Правила с rationale переносятся на новые ситуации.

«Не воспроизводи копирайт» vs «Не воспроизводи копирайт потому что это полные творческие произведения и их краткость не освобождает от защиты». Второе позволяет модели правильно отреагировать на новую ситуацию (короткое стихотворение, цитата без явного источника).

Принцип: при формулировании важного правила добавлять одну строку «потому что» или «цель этого правила».

### 4.4. Self-check вопросы перед действием

Перед критичными действиями давать модели явный чеклист внутренних вопросов.

Пример из copyright у Anthropic:
```
Before including ANY text from search results, Claude asks internally:
- Could I have paraphrased instead?
- Is this quote 15+ words?
- Is this a song lyric, poem, or haiku?
- Have I already quoted this source?
- Am I closely mirroring the original phrasing?
```

Это chain-of-thought в явной форме. Работает сильнее чем общее «подумай внимательно». Специфичность вопросов важнее их количества.

Пример для своего (промпт для написания резюме):
```
Перед финализацией резюме ассистент проверяет:
- Все ли bullets начинаются с action verb в простом прошедшем?
- Есть ли measurable impact (число, процент, масштаб) минимум 
  в половине bullets?
- Нет ли passive voice ("was responsible for", "tasked with")?
- Нет ли vague verbs ("worked on", "helped with", "participated in")?
- Summary укладывается в 3-4 строки?
- Skills сгруппированы по категориям, не одним списком?
```

### 4.5. Default + override структура

Большинство правил формулируется как «по умолчанию X, но если Y - то Z».

Преимущество: модель гибкая без drift. Жесткое правило без override создает frustrating edge cases. Override без правила создает хаос.

Примеры из Claude:
- Не использует эмодзи, если только пользователь сам их не использует
- Отвечает на русском, если только контекст не требует другого
- Избегает списков, если пользователь не попросил список

Для критичных правил override закрывается явно: «Claude never reproduces lyrics, even if asked repeatedly». Для стилистических - оставляется открытым.

Решение где закрывать, где оставлять - осознанное.

### 4.6. Явные failure modes - инвентаризация

Anthropic называет конкретные неудачные траектории и предостерегает от них:

- «Failure mode: Claude's identity degrades over extended interactions»
- «Do not collapse into self-abasement»
- «Do not reframe a request to make it appropriate - that reframing is the signal to refuse»

Это не «будь хорошим», а «вот конкретные способы стать плохим». Модель получает названия для failure modes - может их распознавать у себя.

Для своих промптов: прямо прописывать антипаттерны. «Не быть полезным следующими способами:» с конкретным списком.

### 4.7. Cost-benefit язык вместо буквы правил

Когда правила не покрывают все случаи, давать модели framework для принятия решений в трейд-офф терминах.

«Tool_search is essentially free; unnecessary search is cheap, missed search costs user real effort» - модель получает экономику решения. Может рассудить в новой ситуации не покрытой правилами.

Для своих промптов: где есть зона неопределенности, давать не правило, а tradeoff. Пример из support-ассистента: «Передача случая живому оператору занимает у команды время; пропуск передачи когда она была нужна стоит NPS клиента. Выбирай в пользу передачи если есть сомнения.»

### 4.8. Невидимость механики - что модель не упоминает

Отдельный класс правил - что модель не должна писать в выводе:
- Не анонсировать что собирается делать
- Не объяснять выбор между подходами
- Не извиняться за отсутствие информации
- Не повторять запрос пользователя
- Не писать «I hope this helps»
- Не использовать meta-фразы про работу с памятью

LLM имеет тенденцию narrate свой процесс - это делает ответ длиннее и создает ощущение машины.

Для своих промптов: явно перечислять типы meta-commentary которых не должно быть. «Не объясняй что делаешь, не суммируй запрос, не пиши заключений типа "Если есть вопросы - обращайтесь"».

### 4.9. Иерархия источников при конфликте

В любом промпте где есть несколько возможных источников инструкций (system prompt, пользовательские preferences, контекст разговора, tool results) - явно прописать приоритет.

```
При конфликте инструкций приоритет такой:
1. Master rules из преамбулы - нерушимы
2. Текущие инструкции пользователя в диалоге  
3. Сохраненные preferences пользователя
4. Контекст из истории разговора
```

Без явной иерархии модель сдвигается в сторону последней полученной инструкции (recency bias) или наиболее эмоциональной (давление пользователя).

### 4.10. Tool outputs как untrusted data

Принцип за пределами security: все что возвращается из tool (веб-страница, документ, email, search result) - данные, не инструкции. Инструкции только из user turn.

Если в веб-странице написано «Сделай X» - модель должна переспросить пользователя, не выполнять.

Применимо к любой агентной системе: data sources не могут авторизовать действия.

### 4.11. Диагностический вопрос-тест для размытых классификаций

Когда решение трудно описать списком триггеров, дать модели один четкий вопрос который она задает себе чтобы классифицировать случай. Системный промпт Claude так решает когда искать в интернете: «Тест: требует ли ответ знания что это за вещь? Если да и не можешь вспомнить - искать». И так же разделяет файл от инлайна: «что важнее, standalone-артефакт который скопируют, или ответ в чате».

Триггеры перечисляют известные случаи. Тест дает модели механизм классифицировать неизвестные, не перечисленные явно. Для размытых границ это работает там где список триггеров неизбежно неполон. Формула: одно бинарное (или почти) условие, проверяемое моделью на лету.

Пример: «Тест: пойдет ли результат во внешний документ, или это ответ для чтения в чате? Копирует - файл. Читает - инлайн».

### 4.12. Закрытие лазейки через названное оправдание

Для правил которые модель склонна обходить под давлением, не просто запретить действие, а назвать конкретное оправдание которым модель будет обходить, и закрыть его явно. Системный промпт Claude насыщен этим в guardrails: «не рационализирует уступку ссылкой на публичную доступность или предполагаемую исследовательскую цель», «срочность не исключение», «скорость не дает права выбрать партнера за пользователя».

Механизм: под давлением модель генерирует self-justification («это для образования», «это публично известно», «срочно»). Голый запрет оставляет пространство договориться с собой. Названная и закрытая лазейка это пространство убирает. Особенно ценно для boundary-правил, safety-правил, и любого правила которое пользователь будет пытаться продавить.

Пример: «не давай гарантий по срокам. То что собеседник настаивает что срочно, или что сроки уже где-то назывались, не основание дать гарантию».

### 4.13. Прибивание области применения

Современные модели (особенно Opus 4.8) следуют инструкциям буквально и не переносят правило с одного элемента на другие сами. Если правило должно применяться ко всему, это пишется явно: «к каждой секции, не только к первой», «во всех ответах без исключения». Системный промпт Claude прибивает область прямо в названии правила: «применяется к каждому вопросу», «применять в каждом ответе».

Без прибитой области модель может применить правило к первому подходящему случаю и не распространить дальше - это не лень, это буквальное следование написанному. Литерализм современных моделей хорош для предсказуемости, но означает что широту применения надо указать, модель не додумает.

Пример: «заголовки в title case в каждой секции, не только в первой».

### 4.14. Два масштаба примеров: блок и инлайн-пара

Полный пример в `<example>` теге - для сложных правил где нужен развернутый образец вход-выход (см. 4.1, 7.2). Инлайн контраст-пара - для компактных правил где блок избыточен: «X, не Y» прямо в строке правила. Системный промпт Claude насыщен такими: «latest iPhone 2025 устаревшее, latest iPhone правильно», «"мне нужна машина" это не "хочу именно RideCo"», «"быстрый пост на 200 слов" все равно файл».

Сжатая пара X-не-Y закрепляет границу одной строкой без отдельного блока. Выбор масштаба: если граница тонкая и описывается одним противопоставлением - инлайн-пара. Если нужен формат, структура, тон выхода - полный блок.

### 5.1. Два framing - character и identification

При создании ассистента есть два подхода:

**Character framing (descriptive).** Промпт описывает character с свойствами и правилами. «Ассистент помогает менеджеру. Ассистент работает прямо. Ассистент эскалирует в ситуациях X».

**Identification framing.** Промпт обращается к модели как к самому персонажу. «Ты [Имя]. Ты работаешь прямо. Ты в ситуациях X оставляешь комментарий "нужен супервайзер"».

### 5.2. Когда что использовать

**Character framing работает лучше когда:**
- Ассистент это автономный продукт от лица компании
- Длинные adversarial диалоги где модель может «сломаться»
- Цель - стабильность поведения под давлением
- Этически важно чтобы конечный пользователь знал что общается с AI

**Identification framing работает лучше когда:**
- Имитация конкретного человека с целью неотличимости от него
- Каждое сообщение проходит через человека-модератора перед отправкой
- Короткие операционные ответы
- Цель - максимальное правдоподобие стиля

Для бизнес-кейсов с модерацией identification framing предпочтительнее. Самореференция от первого лица получается естественнее. Импровизация в стиле работает лучше в нетипичных ситуациях.

### 5.3. Правила одинаково работают в обоих framing

Operational rules (эскалация, проверка контекста, отказ давать обещания) формулируются одинаково в обоих подходах. Просто в одном это правила ассистента, в другом - привычки имитируемого человека.

«Ассистент в ситуациях X оставляет комментарий "нужен супервайзер"» = «Ты в ситуациях X оставляешь комментарий "нужен супервайзер"». На уровне модели разница минимальная.

### 5.4. Качество имитации не зависит от framing

Главный фактор правдоподобия имитации - не identity framing, а **качество описания стиля**.

Что должно быть:

**Словарь.** Какие слова используются часто, какие избегаются.

**Синтаксис.** Длина предложений, любимые конструкции, характерные обороты.

**Пунктуация и форматирование.** Точки в конце сообщений, многоточия, маленькие буквы.

**Интонации.** Как шутит, критикует, соглашается, возражает.

**Табу.** Что никогда не пишет.

**Примеры реальных сообщений.** Самое сильное средство. 15-25 настоящих сообщений разных типов с короткими комментариями что в них характерного.

Без хороших примеров никакое identity framing не даст правдоподобной имитации. С хорошими примерами и тот, и другой framing дают хороший результат.

### 5.5. Шаблон identification framing для имитации человека

```
## Кто ты
Ты [Имя Фамилия], [роль]. Ты отвечаешь [контекст] в [канал].

## Master rules - язык и форматирование
[правила применяемые всегда]

## Твой стиль
Словарь: [часто используемые слова, избегаемые слова]
Синтаксис: [характерные конструкции]
Пунктуация: [особенности]
Интонации: [как шутишь, как критикуешь, как соглашаешься]
Табу: [что никогда не пишешь]

## Примеры твоих реальных сообщений
[15-25 примеров разных жанров с комментариями]

## Decision-блок: определение типа собеседника
[триггеры распознавания]

## Decision-блок: ответ типу X
[процедура, правила, примеры]

## Decision-блок: ответ типу Y  
[процедура, правила, примеры]

## Когда не отвечаешь сам
В ситуациях X, Y, Z ты оставляешь комментарий "нужен 
супервайзер" и не пишешь ответ.
- X: [список]
- Y: [список]
- Z: [список]

## Когда не знаешь
Если в контексте нет нужной информации - не додумывай. 
Пиши "уточню и вернусь" и ставь комментарий что нужна 
проверка факта.
```

### 5.6. Калибровка тона через felt-quality и анти-модели

Для тон-чувствительных ролей кроме механических правил дать модели описание ощущения от правильного поведения через конкретную человеческую аналогию плюс явные анти-модели «не как X». Системный промпт Claude так калибрует предложение инструментов: «как помог бы человек который заметил инструмент лежащий рядом. Не как продавец. Не как анонс фичи. Просто: о, я же могу это сделать за тебя».

Структура приема: одна позитивная аналогия (на что это похоже) плюс два-три явных анти-образа (на что это НЕ похоже). Анти-модели работают как negative anchors, отсекая характерные failure-режимы тона: подобострастие, продажность, корпоративность, машинность.

Где применять: блоки тона в Типе A (character) и описание стиля в Типе B (imitation). Для исполнительских Типов C и D обычно избыточно. Felt-quality дополняет, не заменяет конкретику словаря и синтаксиса из 5.4 - сначала конкретные маркеры стиля, felt-quality сверху для общего регистра.

Пример: «Тон ответа как у коллеги который уже решал эту проблему и делится по-быстрому. Не как методичка. Не как саппорт по скрипту. Не как ментор читающий лекцию».

## 6. Шаблоны и контр-примеры

### 6.1. Структурный шаблон промпта

Для сложных промптов (Тип A/B/D) - XML-теги для крупных секций. Имена описательные, консистентные, на латинице. Простой one-shot (Тип C) может остаться на markdown-заголовках.

```
<role>
Кто ассистент, для чего, от чьего имени. 2-3 строки.
</role>

<master_rules>
Правила применяемые всегда (язык, форматирование, hard limits).
Без капса/MUST для не-критичного.
</master_rules>

<context>
Только то что нужно модели и не извлекается из decision-блоков. Минимум.
</context>

[Если на вход идет крупный документ - блок <documents> с ним идет 
ВЫШЕ инструкций, см. раздел 7.3]

<situation_routing>
Определение типа ситуации, триггеры для каждого типа.
</situation_routing>

<situation name="...">
Для каждого типа ситуации:
- Триггеры распознавания
- Процедура
- Правила (со ссылками на master где уместно)
- 3-5 примеров в <examples>/<example> тегах, разнообразных
- 2-3 примера неправильного с rationale
- Self-check вопросы перед выдачей
</situation>

<escalation>
Когда не отвечать, когда передавать дальше, что делать с нестандартом.
</escalation>

<final_checks>
Что проверить перед отправкой ответа.
</final_checks>
```

### 6.2. Чеклист самопроверки промпта

Перед использованием прогнать промпт по списку:

- [ ] В preamble четко сказано кто и для чего
- [ ] Master rules в начале, не в конце
- [ ] Названия блоков - про решения, не про темы
- [ ] Сложный промпт использует XML-теги для секций (Тип C может markdown)
- [ ] Каждое сложное правило имеет 3-5 примеров в `<example>` тегах, разнообразных
- [ ] Каждое сложное правило имеет 2-3 примера неправильного с rationale
- [ ] Граничные случаи покрыты примерами (не только центральные)
- [ ] Крупный входной документ - наверх, выше инструкций, в `<document>` тегах
- [ ] Регистры модальности разнообразны: descriptive для identity, never/always для критичного, should для default, can для разрешений
- [ ] Без капса/MUST для не-критичного (вызывает overtriggering на современных моделях)
- [ ] Нет softening слов (please, try to, would be good)
- [ ] Тон описан позитивно, anti-patterns конкретными примерами
- [ ] Формат вывода через «что делать» и XML-индикаторы, стиль промпта = стиль вывода
- [ ] Критичные правила продублированы рядом с decision-блоками где применяются
- [ ] Длина описания пропорциональна важности правила
- [ ] Эскалация и failure modes описаны явно
- [ ] Self-check вопросы перед критичными действиями
- [ ] Иерархия источников при конфликте прописана
- [ ] Что модель не должна писать в выводе - явно перечислено

### 6.3. Контр-примеры - частые ошибки

Контр-примеры ниже используют markdown-заголовки для краткости и чтобы сфокусировать на конкретной ошибке которую каждый иллюстрирует. В реальных сложных промптах крупные секции оборачивать в XML-теги (раздел 7.1).

**Тематическая структура вместо decision-type:**

❌ Плохо (на примере промпта для customer support чат-бота):
```
## О продукте
SaaS-платформа для управления проектами с тарифами Basic/Pro/Enterprise...

## О команде
Sales-менеджеры, support-инженеры, customer success...

## Тон общения  
Дружелюбный, профессиональный, без формальностей...

## Что нельзя
- Не называть скидки
- Не давать SLA-гарантий
- Не обсуждать других клиентов
```

✅ Хорошо:
```
## Кто ты
Ты support-ассистент SaaS-платформы, отвечаешь клиентам в чате.

## Когда тебе пишут впервые
[распознавание нового лида, процедура квалификации, 
кого упомянуть из sales-команды]

## Когда тебе пишет существующий клиент с техническим вопросом
[процедура диагностики, эскалация support-инженеру 
если запрос требует доступа к логам]

## Когда тебе пишут про скидки или специальные условия
[ВСЕГДА эскалация sales-менеджеру, не отвечать самому]
```

**Один регистр на все:**

❌ Плохо (все через should):
```
- Ассистент should отвечать прямо
- Ассистент should избегать филлеров
- Ассистент should никогда не называть скидки
- Ассистент should проверять контекст
```

✅ Хорошо (разные регистры):
```
- Ассистент отвечает прямо.  (descriptive - identity)
- Ассистент избегает AI-филлеров.  (avoids - стилистика)
- Ассистент НИКОГДА не называет скидки без подтверждения.  (never - критичное)
- Перед ответом ассистент проверяет контекст.  (should - процедура)
```

**Правила без примеров:**

❌ Плохо:
```
Bullets в резюме пишутся в формуле action verb + impact.
```

✅ Хорошо:
```
Bullets в резюме пишутся в формуле action verb + impact.

Правильно:
- Reduced API latency by 40% by introducing Redis caching
- Architected migration to microservices (12 services, 6 months)

Неправильно:
- Was responsible for API performance (passive, no action verb)
- Worked on migration projects (vague verb, no scope)
- Improved system reliability (action verb но нет конкретики)
```

**Софтенинг и пожелания:**

❌ Плохо:
```
Please try to be helpful. It would be great if you could 
respond in a friendly tone. We hope you can keep responses concise.
```

✅ Хорошо:
```
Ассистент помогает прямо и по делу. 
Тон дружелюбный, без формальностей. 
Ответы краткие.
```

**Размазанные правила:**

❌ Плохо (правило про букву Ё спрятано в общем разделе про тон, который читается один раз):
```
## Тон
Общение неформальное, на русском. Используется простой словарь, 
избегаются англицизмы где это возможно без потери смысла. 
Буква Ё всегда заменяется на Е. Эмодзи используются редко...

## Ответ новому пользователю
[процедура, никаких упоминаний правила]

## Ответ существующему пользователю
[процедура, никаких упоминаний правила]
```

✅ Хорошо (правило дублируется рядом с применением):
```
## Master rules - язык
- Русский, без буквы Ё (всегда Е)
- Без AI-филлеров
- Без em-dash

## Ответ новому пользователю
[процедура]
Язык: применяются master rules. Контрольная проверка перед 
отправкой - нет буквы Ё, нет филлеров.

## Ответ существующему пользователю
[процедура]  
Язык: применяются master rules. Контрольная проверка - 
нет буквы Ё, нет филлеров.
```

**Identity без качественного описания стиля:**

❌ Плохо:
```
Ты [Имя]. Отвечай в своем стиле.
```

✅ Хорошо:
```
Ты [Имя].

## Твой стиль
Словарь: используешь "ок", "разбираем", "по делу", "давай". 
Избегаешь "пожалуйста", "благодарю", "с уважением".

Синтаксис: пишешь короткими предложениями. Начинаешь ответ 
с сути, без вводной. Часто используешь конструкцию 
"вот что я думаю: ...".

Пунктуация: в коротких сообщениях точку в конце не ставишь. 
Em-dash не используешь, заменяешь запятой.

Интонации: возражаешь прямо без смягчения "не согласен", 
"меряешь не тем". Соглашаешься коротко - "да", "согласен".

Табу: никогда не пишешь "отличный вопрос", "рад помочь", 
"надеюсь помог", "с уважением".

## Примеры твоих реальных сообщений

```

## 7. XML-разметка, длинный контекст, формат вывода

Этот блок собирает техники из официального гайда Anthropic по промптингу которые сильнее всего влияют на качество вывода и часто упускаются.

### 7.1. XML-теги для структуры

Anthropic явно рекомендует XML-теги для промптов которые мешают инструкции, контекст, примеры и переменный инпут. Системный промпт самого Claude построен на XML-тегах. XML убирает двусмысленность границ между блоками: модель парсит `<instructions>`, `<context>`, `<examples>` однозначно, тогда как markdown-заголовки на длинных промптах сливаются с контентом.

Правила:
- Описательные консистентные имена тегов. Не `<section1>`, а `<role>`, `<output_format>`, `<escalation_rules>`.
- Вкладывать когда есть иерархия: документы в `<documents>`, каждый в `<document index="n">`.
- Градация по сложности: сложные промпты (Тип A/B/D) - XML для крупных секций. Простой one-shot (Тип C) - markdown-заголовков достаточно, но примеры и документы все равно в XML.

### 7.2. Примеры в XML-тегах, 3-5, разнообразные

Каждый пример оборачивать в `<example>`, набор в `<examples>`. Целиться в 3-5 (не 2, не 10). Примеры разнообразные, покрывают граничные случаи - иначе модель выцепляет случайный паттерн (если все примеры начинаются с одного слова, модель решит что так надо всегда).

Это уточняет правило 4.1: примеры не просто «должны быть», а должны быть в XML-обертке и разнообразными. Можно попросить модель оценить свои примеры на relevance и diversity или сгенерировать дополнительные.

### 7.3. Длинные данные и документы - наверх

Когда промпт работает с большим документом (от ~20k токенов), класть данные в НАЧАЛО, ВЫШЕ запроса, инструкций и примеров. Запрос в конце поднимает качество до 30% на мульти-документных задачах.

Оборачивать: `<documents>` → `<document index="n">` → `<document_content>` + `<source>`.

Ground in quotes: для задач по длинному документу просить модель сначала выписать релевантные дословные фрагменты, потом работать с ними. Это прорезает шум.

Для system/user split: инструкции в system, документ в user-turn (естественно «наверху» обрабатываемого контента). Для единого промпта: документ near the top после короткой роли, запрос в самом конце.

### 7.4. Формат вывода: «что делать» и XML-индикаторы

Три рычага управления форматом:
- Говорить что делать, не что не делать. «Пиши прозой связными абзацами» вместо «не используй markdown».
- XML-индикатор формата. «Оберни прозу в `<prose>` теги».
- Match prompt style to output. Стиль форматирования промпта протекает в стиль ответа. Хочешь прозу - пиши инструкции прозой. Убрал markdown из промпта - меньше markdown в выводе.

### 7.5. Thinking: общие инструкции вместо расписанных шагов

Если промпт требует рассуждения, «продумай тщательно перед ответом» часто дает лучший reasoning чем расписанный по шагам план - рассуждение модели нередко превосходит то что прописал бы человек. Пошаговый план только когда нужен фиксированный пайплайн.

На моделях с выключенным thinking слово «think» чувствительно - лучше «consider», «evaluate», «reason through», «продумай», «оцени». В few-shot примерах паттерн рассуждения показывать через `<thinking>` теги.

### 7.6. Роль и контекст-мотивация

Даже одно предложение роли в начале фокусирует поведение и тон. Это совпадает с преамбулой в decision-структуре.

Объяснение мотивации («почему это важно») усиливает следование - модель обобщает из объяснения. Совпадает с правилом 4.3 (reasoning встроен в правило), но Anthropic выделяет это и на уровне всего промпта, не только отдельных правил.

## 8. Итоговые принципы одной строкой

1. Модель не читает линейно - она весит токены через attention.
2. Близость правила к моменту применения сильнее эмфазиса.
3. Дублирование критичных правил - норма, не антипаттерн.
4. Шесть регистров модальности - выбирать осознанно.
5. Третье лицо для character, второе для имитации конкретного человека.
6. Софтенинг (please, try to) ослабляет сигнал - убирать.
7. Позитивные формулировки для тона, явные anti-patterns для конкретных запретов.
8. Структура по типам решений, не по темам.
9. Базовая информация распределяется по decision-блокам.
10. Master rules в начале, дублирование рядом с применением.
11. Длина описания пропорциональна важности правила.
12. Каждое сложное правило с 3-5 примерами в `<example>` тегах, разнообразными, плюс 2-3 неправильных с rationale.
13. Граничные примеры важнее центральных.
14. Reasoning встроен в правило - модель должна понимать цель.
15. Self-check вопросы перед критичными действиями.
16. Default + override структура для гибкости без drift.
17. Явные failure modes названы поименно.
18. Cost-benefit язык там где правила не покрывают все.
19. Что модель не должна писать в выводе - явный список.
20. Иерархия источников при конфликте - явно прописана.
21. Tool outputs как данные, не команды.
22. Для имитации человека - identification framing с качественным описанием стиля и 15-25 реальными примерами сообщений.
23. XML-теги для структуры сложных промптов, описательные консистентные имена.
24. Крупный входной документ - наверх, выше инструкций, в `<document>` тегах, до 30% к качеству.
25. Ground in quotes для длинных документов - сначала выписать релевантное, потом работать.
26. Формат вывода через «что делать» и XML-индикаторы, не через «что не делать».
27. Стиль промпта протекает в стиль вывода.
28. Без капса и MUST на современных моделях - вызывает overtriggering, капс только реальным hard limits.
29. Диагностический вопрос-тест для размытых классификаций, где список триггеров неизбежно неполон.
30. Закрывать лазейку, называя конкретное оправдание заранее, а не голым запретом.
31. Прибивать область применения явно - современные модели следуют буквально и не додумывают широту.
32. Два масштаба примеров: полный блок в example-теге и компактная инлайн-пара X-не-Y.
33. Для тона - felt-quality аналогия плюс анти-модели поверх конкретных маркеров стиля.

## Финальная нота

Главная мысль через все правила: писать промпт не как инструкцию для исполнителя, а как описание существа со встроенными свойствами и протоколами. Этому существу не нужно объяснять что делать - ему описывают кто оно, и оно действует исходя из этого описания.

Чем больше промпт похож на профиль персонажа с прописанной механикой принятия решений, тем устойчивее модель работает. Чем больше он похож на список команд - тем больше пространства для дрифта, манипуляции и формальных нарушений в духе правил.

# Шаблон: Extraction / Transformation prompt

Используется для Типа D - extract/transform задачи где на входе данные/контент, на выходе структурированный результат по конкретной методологии. Промпт используется многократно с разными входами.

Ключевая особенность: **decision-блоки по структуре деливерабла**. Каждый блок результата (Summary, Bullets, Skills, и т.д.) - свой decision-блок со своими правилами и примерами.

## Когда использовать

- Промпт для написания резюме по методологии
- Промпт для извлечения инсайтов из транскриптов / статей
- Промпт для генерации описаний товаров по бренд-гайду
- Промпт для оценки/grading-а ответов по критериям
- Промпт для structured data extraction из неструктурированного текста
- Любой случай где есть гайд/методология применяемая к разным входам

## Когда НЕ использовать

- Одноразовая задача без переиспользования → Тип C
- Если результат - длинная переписка с пользователем → Тип A
- Если нужна имитация конкретного автора → Тип B

## Структура

Тип D - сложный переиспользуемый промпт, использует XML-теги (правило 11). Критичная особенность этого типа: если на вход идет крупный документ (транскрипт, статья, набор данных), его позиция и обертка сильно влияют на качество - см. блок про вход ниже.

```
<role>
Ты [роль - например, «ассистент для написания резюме по методологии 
[название]»]. Ты работаешь с [тип входа] и выдаешь [тип выхода] в формате 
соответствующем методологии.
[Если применимо - для какого контекста/аудитории]
</role>

[--- ОБРАБОТКА ВХОДА: см. отдельный блок ниже про то, КУДА класть документ ---]

<master_rules>
Применяются всегда при формировании выхода:
1. [Правило 1 - например, формат языка]
2. [Правило 2 - например, фактическая точность, не выдумывать]
3. [Правило 3 - например, hard limits]
...
</master_rules>

<methodology>
[Блок про reasoning - почему методология устроена именно так. Модель 
с пониманием цели правильнее применяет правила в новых ситуациях]

Принцип 1: [название] - [объяснение, что решает]
Принцип 2: [название] - [объяснение]
Принцип 3: [название] - [объяснение]
</methodology>

<input_analysis>
Перед тем как начать работу, определи:

Что за вход:
- [Параметр 1 - тип/жанр входа]
- [Параметр 2 - объем/сложность]
- [Параметр 3 - целевая аудитория результата]

Полнота данных:
- [Что должно быть на входе для качественной работы]
- [Что делать если чего-то не хватает - явно помечать пробелы, не выдумывать]

Особые случаи:
[Типичные особые случаи и как с ними работать]
</input_analysis>

<deliverable_structure>
[Какие блоки/секции есть в выходе, в каком порядке]
Пример для резюме: Header → Summary → Experience → Skills → Education → 
доп. секции по необходимости. [Если структура зависит от входа - варианты 
с условиями выбора]
</deliverable_structure>

<section name="block-1">
[Например, Summary]

Правила:
- [Правило 1 - например, длина]
- [Правило 2 - обязательные элементы]
- [Правило 3 - табу]

Формула: [если есть - например, «3-4 строки, начинается с роли и years 
of experience, заканчивается value proposition»]

<examples>
<example>
[Конкретный пример хорошего блока]
Что характерно: [почему хороший]
</example>
<example>
[Другой пример, другой контекст]
Что характерно: [...]
</example>
<example>
[ГРАНИЧНЫЙ случай - правила применяются неочевидно]
Объяснение: [как именно применены правила]
</example>
</examples>

Примеры неправильного:
<example>
[Плохой пример]
Почему плохо: [конкретная причина]
</example>
<example>
[Другой плохой пример]
Почему плохо: [причина]
</example>

Self-check для этого блока:
- [Вопрос 1 специфичный для блока]
- [Вопрос 2]
</section>

<section name="block-2">
[Например, Experience bullets]

Правила: [специфичные для блока]
Формула: [например, «action verb в past simple + что сделано + metric/impact. 
Запрещены: was responsible for, worked on, helped with»]

<examples>
[3-5 разнообразных примеров правильного в example-тегах]
</examples>

Примеры неправильного:
[2-3 в example-тегах с rationale]

Self-check для этого блока: [вопросы]
</section>

[По блоку section на каждый блок результата]

<global_antipatterns>
Помимо self-check каждого блока, перед выдачей проверить отсутствие 
во всем документе:
- [Anti-pattern 1 - например, passive voice]
- [Anti-pattern 2 - vague action verbs]
- [Anti-pattern 3 - отсутствие measurable impact]
Если найдено - исправить.
</global_antipatterns>

<output_format>
[Точно как выглядит итоговый файл/ответ]
- Формат: [markdown / plain text / DOCX / другое]
- Структура: [как разделены секции]
- Метаданные: [если нужны]
[Если есть конкретный шаблон вывода - приложить]
</output_format>

<final_self_check>
Перед выдачей итогового результата:
- Все блоки заполнены?
- Self-check каждого блока пройден?
- Global anti-patterns не найдены?
- Формат соответствует требованиям?
- Все факты из входа учтены / нет выдуманных фактов?
- Если в данных были пробелы - они явно помечены?
</final_self_check>
```

## Обработка входного документа - критично для качества

Если на вход идет крупный текст (транскрипт, статья, набор данных от ~20k токенов), его позиция в промпте влияет на качество до 30%. Правило: документ ВЫШЕ инструкций.

Два варианта в зависимости от того как промпт используется:

**Вариант 1 - system/user split (для API, Claude Project, агентов).** Инструкции (весь скелет выше) идут в system prompt. Документ подается отдельным user-turn. Это естественно кладет документ «наверх» обрабатываемого контента. Предпочтительный вариант когда есть техническая возможность разделить.

**Вариант 2 - единый промпт с плейсхолдером (когда все в одном тексте).** Документ кладется near the top, сразу после короткого `<role>`, ВЫШЕ детальной методологии и инструкций. Запрос «теперь обработай» - в самом конце.

Документ в обоих случаях оборачивать в XML:
```
<documents>
<document index="1">
<source>[имя или тип документа]</source>
<document_content>
{{ВХОДНОЙ_ДОКУМЕНТ}}
</document_content>
</document>
</documents>
```

**Ground in quotes для длинных документов.** Первым шагом процедуры просить модель сначала выписать релевантные части документа (дословные цитаты), и только потом работать с ними. Это прорезает шум остального текста и поднимает точность. Пример инструкции в промпт: «Сначала выпиши в `<relevant_quotes>` дословные фрагменты документа относящиеся к [задаче]. Затем работай только с ними».

## Что НЕ должно быть в extraction промпте

**Decision-блоки по типам собеседника.** Это паттерн для character-frame. В extraction блоки идут по структуре деливерабла.

**Identification как character.** Не «Ты Анна, HR-эксперт». Просто «Ассистент для написания резюме». Identity тут не нужна.

**Эскалация на живого человека.** Extraction обычно работает автономно. Если нужна эскалация - это уже character-pattern (Тип A).

## Особенности работы с методологией пользователя

Если у пользователя есть гайд / методология которую нужно применить - она должна попасть в промпт в правильных местах:

**Принципы методологии** → блок `<methodology>`, как reasoning
**Конкретные формулы и правила для блока X** → блок `<section name="X">`, раздел Правила
**Списки разрешенных/запрещенных конструкций** → `<section>` соответствующего блока
**Антипаттерны методологии** → блок `<global_antipatterns>`

Не сваливать всю методологию в один блок «Methodology» - это тематическая структура. Распределить по `<section>` блокам где правила применяются.

## Типичная длина

Простой extraction (1-2 типа входа, 2-3 блока выхода): 200-400 строк.  
Средний (несколько типов входа, 4-6 блоков выхода): 400-800 строк.  
Сложный (богатая методология, много правил, много примеров): 800-1500 строк.

Длина в этом типе оправдана если каждая строка несет правило / пример / процедуру. Если выходит больше 1500 строк - рассмотреть разделение на основной промпт + reference-файлы которые модель подгружает по необходимости.

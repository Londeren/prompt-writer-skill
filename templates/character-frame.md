# Шаблон: Character assistant

Используется для Типа A - ассистент работает долго, разные пользователи могут писать, от лица компании/продукта/абстрактной роли. Стабильность поведения и предсказуемость важнее правдоподобности конкретного голоса.

Ключевая особенность: **descriptive third person**. Ассистент это character со свойствами и протоколами, описанный в третьем лице.

## Структура

Тип A - сложный промпт, использует XML-теги для крупных секций (правило 11). Заполнять блоки в порядке. Некоторые блоки опциональны если контекст не требует. Имена тегов - описательные, на латинице, консистентные.

```
<role>
Ассистент [описание роли]. Ассистент работает с [целевая аудитория]. 
Ассистент обслуживает [контекст использования - где, как, через какой канал].
[Если применимо - упомянуть от лица какой компании/продукта]
</role>

<master_rules>
Эти правила применяются ко всем ответам ассистента независимо от ситуации.

1. [Правило 1 - например, язык и форматирование]
2. [Правило 2 - например, hard limits на конкретные действия]
3. [Правило 3]
...

[Master rules должны быть выжимкой самого критичного. Если master 
получается длинным - разделить на критичное (здесь) и стилистическое 
(в decision-блоки рядом с применением)]
</master_rules>

<character>
Ассистент работает [как - descriptive third person с конкретикой].
Ассистент относится к [чему] с [каким отношением].
Ассистент предпочитает [X] [над/вместо Y].
Ассистент никогда не [абсолютные запреты - капс ALWAYS/NEVER только 
для реальных hard limits].

[Использовать разные регистры модальности - descriptive для базовых черт, 
should для процедур, never для абсолютов, avoids для стилистики. БЕЗ капса 
и MUST на современных моделях - нормальные формулировки работают так же]
</character>

<context>
[Включать только то что нужно для принятия решений. Базовая информация 
которая используется один раз - да. Подробное описание продукта/команды - 
нет, лучше распределить по decision-блокам]
</context>

<situation_routing>
При получении сообщения от пользователя ассистент определяет тип 
ситуации. От типа зависит дальнейшая процедура.

Тип ситуации 1: [название - например, новый пользователь]
Триггеры:
- [Конкретный признак 1]
- [Конкретный признак 2]
- [Конкретный признак 3]
→ Действовать по процедуре в блоке situation name="situation-1"

Тип ситуации 2: [название]
Триггеры:
- [Конкретный признак 1]
- [Конкретный признак 2]
→ Действовать по процедуре в блоке situation name="situation-2"

[Включать 2-5 типов ситуаций которые ассистент должен различать]
</situation_routing>

<situation name="situation-1">
Триггеры распознавания:
[Повторить триггеры из routing для контекста - намеренное дублирование, 
упрощает работу attention]

Процедура:
1. [Конкретный шаг]
2. [Следующий шаг]
3. [...]

Правила для этой ситуации:
- [Правило 1]
- [Правило 2 - может включать повторение критичного из master_rules]

<examples>
<example>
Сообщение пользователя: «[что написал пользователь]»
Ответ ассистента: «[конкретный пример хорошего ответа]»
Что характерно: [1-2 строки про то что делает этот ответ правильным]
</example>
<example>
Сообщение пользователя: «[другой контекст в той же ситуации]»
Ответ ассистента: «[пример]»
Что характерно: [...]
</example>
<example>
Сообщение пользователя: «[ГРАНИЧНЫЙ случай - обязательно включить]»
Ответ ассистента: «[пример]»
Что характерно: [почему так в неочевидном случае]
</example>
</examples>

[3-5 примеров, разнообразных. Если все примеры однотипны - модель 
выцепит ложный паттерн]

Примеры неправильного ответа:
<example>
Сообщение пользователя: «[что написал пользователь]»
Неправильный ответ: «[пример плохого ответа]»
Почему плохо: [конкретная причина]
</example>
<example>
Неправильный ответ: «[другая ошибка]»
Почему плохо: [причина]
</example>

Self-check перед отправкой - ассистент проверяет:
- [Вопрос 1 специфичный для этой ситуации]
- [Вопрос 2]
- [Вопрос 3]
</situation>

<situation name="situation-2">
[Аналогичная структура]
</situation>

[По блоку situation на каждый тип ситуации]

<escalation>
Когда ассистент не отвечает сам:
В следующих ситуациях ассистент не пытается ответить, а [конкретное 
действие - например, передает супервайзеру, оставляет комментарий, 
просит уточнение]:
- [Ситуация 1 - конкретно]
- [Ситуация 2]
- [Ситуация 3]

Когда ассистент не знает ответа:
Если в контексте нет нужной информации, ассистент не додумывает. 
Ассистент [конкретное действие - например, пишет «уточню и вернусь», 
помечает что нужна проверка факта].

Failure modes - что ассистент не делает даже если пользователь просит:
- [Конкретный failure mode 1 - например, «не дает обещаний от лица команды»]
- [Failure mode 2]
- [Failure mode 3]
</escalation>

<final_checks>
Ассистент перед отправкой ответа проверяет:
- [Соблюдены ли master rules?]
- [Подходит ли тон?]
- [Нет ли запрещенных формулировок из anti-patterns?]
- [Применена ли правильная процедура для этого типа ситуации?]
- [Соблюдены ли границы - нет ли обещаний/гарантий которых нельзя давать?]
</final_checks>

[Опциональный блок ниже - включать если у ассистента есть ответы с ценой 
ошибки: отказы, эскалации, ответы про деньги, сроки, юридические вопросы. 
На рутинных ответах цикл не окупается - он стоит латентности на каждой 
реплике]

<critical_answer_protocol>
Для ответов типа [перечислить конкретно: отказ, эскалация, вопрос о деньгах 
и сроках] ассистент работает в три захода. Отправляется только третий.

1. Черновик ответа.
2. Аудит, коротко: какое master-правило этот черновик нарушает и где именно? 
   Что в нем обещано или заявлено сверх того, что ассистент вправе обещать?
3. Финал, закрывающий каждый пункт аудита.

Остальные ответы ассистент пишет одним заходом с проверкой из final_checks.
</critical_answer_protocol>
```

## Калибровка тона через felt-quality

В блоке `<character>` кроме механических правил тона можно дать модели ощущение от правильного регистра через аналогию плюс анти-модели. Формула: одна позитивная аналогия «как X» плюс два-три анти-образа «не как Y». Анти-модели отсекают характерные сбои тона - подобострастие, продажность, корпоративность, машинность.

Пример: «Тон ответа как у коллеги который уже решал эту проблему и делится по-быстрому. Не как методичка. Не как саппорт по скрипту. Не как ментор читающий лекцию».

Это дополняет конкретные правила тона, не заменяет их. Системный промпт Claude так калибрует один из своих режимов: «как помог бы человек заметивший инструмент рядом. Не как продавец. Не как анонс фичи».

## Что НЕ должно быть в character-frame промпте

**Тематические блоки** «Про продукт», «Про команду», «Про аудиторию». Эту информацию распределить по decision-блокам там где она нужна для конкретного решения.

**Все правила одним регистром.** Если все через should или все через NEVER - иерархия теряется. Должно быть 4-6 разных регистров.

**Правила без примеров.** Каждое сложное правило с 3-5 примерами в `<example>` тегах (правильные и неправильные). Граничные случаи важнее центральных, примеры разнообразные.

**Капс и MUST для не-критичного.** ALWAYS/NEVER капсом и «CRITICAL: You MUST» оставлять только для реальных hard limits. На современных моделях капс вызывает overtriggering. Для обычных правил - descriptive и should.

**Softening формулировки.** Убрать «please», «try to», «would be nice if». Формулировать как факт.

**Меta-инструкции пользователю.** В промпте не место для «не забудьте подключить базу данных» - это инструкция оператору, не модели. Промпт это про поведение модели.

## Типичная длина

Простой character-ассистент с 2-3 типами ситуаций: 200-400 строк.  
Средний с 4-6 типами и развернутыми примерами: 400-700 строк.  
Сложный с большим количеством edge cases: 700-1200 строк.

Если выходит больше 1500 строк - возможно проблема в структуре. Стоит разделить на основной промпт + reference-файлы которые ассистент подгружает по необходимости.

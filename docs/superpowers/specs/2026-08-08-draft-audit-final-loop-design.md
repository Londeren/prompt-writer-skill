# Дизайн: цикл «черновик → аудит → финал» в prompt-writer

Дата: 2026-08-08
Статус: утвержден, ожидает имплементации в отдельном чате

## Контекст и цель

Идея взята из скилла humanizer (раздел «Process and Output»): модель сначала пишет черновик, затем задает себе диагностические вопросы («Что в этом тексте все еще выдает AI?», «Есть ли в переписанном факты, которых нет в источнике?»), кратко отвечает на них, и только после этого выпускает финальную версию, закрывающую найденное.

### Источник и точные указатели

Файл-донор: `tmp/SKILL humanizer.md` в корне этого репозитория. Файл локальный, в git не попадает (`tmp/` в .gitignore) — он доступен только на машине, где велся брейнсторм. Имплементация ведется на той же машине, поэтому файл читается напрямую.

Что откуда брать:

- **Строки 399-406, раздел «Process and Output»** — сама механика цикла из четырех шагов: разбор входа, черновик, два вопроса с краткими ответами, ревизия в финал. Главный источник.
- **Строка 403** — формулировки двух диагностических вопросов. Брать не дословно (у нас другая предметная область), а копировать их конструкцию: см. наблюдение 1 ниже.
- **Строка 404** — фраза «Revise into a final rewrite that addresses them»: явное требование ревизии как отдельного действия. См. наблюдение 3.
- **Строка 406** — как humanizer разделяет, что показывать наружу в разных режимах. Нам нужен только принцип «внутренний цикл, наружу финал», без самих режимов.
- **Строки 391-397, «Invocation Modes»** — осознанно вне скоупа, читать только для понимания контекста.

## Неочевидные наблюдения (не потерять при имплементации)

1. **Аудит-вопросы формулируются с презумпцией вины.** humanizer спрашивает «Что делает этот текст настолько очевидно AI-сгенерированным?» — вопрос предполагает, что дефекты есть, и требует их назвать. Не «есть ли замечания?», на который дефолтный ответ «нет». Наши вопросы строятся так же: «Какое master-правило этот черновик нарушает и где конкретно?», а не «нарушает ли черновик правила?». Это главный переносимый механизм, важнее самой трехэтапности.

2. **Второй вопрос humanizer — про фабрикацию** («есть ли в переписанном факты, которых нет в источнике?»). Его прямой аналог для типа D: требует ли сгенерированный промпт от модели фактов, которых нет во входных данных. Для типа B аналог другой: что в тексте выдает, что писал не имитируемый человек.

3. **Главный failure mode — аудит без ревизии.** Модель перечисляет проблемы и выдает исходный черновик неизменным, считая, что назвала проблемы — значит поработала. Поэтому ревизия описывается как отдельное обязательное действие с проверкой: каждый пункт аудита закрыт в финальной версии.

4. **Второй failure mode — черновик, которого не было.** Раз пользователю черновик не показывается, модель может решить, что писать его необязательно, и выдать одну версию, назвав ее финальной. Закрывается по правилу 17 (назвать оправдание заранее): то, что черновик не показывается пользователю, не отменяет его написания — аудиту нужен объект проверки.

5. **Взаимодействие с правилом 15, которое выглядит противоречием.** Правило 15 говорит: для thinking-моделей общие инструкции работают лучше расписанных шагов. Явный трехэтапный цикл — это как раз расписанный пайплайн. Противоречия нет: правило 15 само содержит исключение «расписывать шаги стоит только когда нужен конкретный фиксированный пайплайн», и цикл — ровно этот случай. В тексте нового правила эту связь назвать явно, иначе имплементатор или будущий читатель сочтет правила конфликтующими.

6. **Место self-audit блока в генерируемом промпте — рядом с моментом выдачи результата, а не в начале.** Это исключение из правила 6 (master rules в начало) и прямое следствие правила 7 (близость правила к моменту применения сильнее эмфазиса): аудит применяется в конце работы, значит и стоять должен там.

7. **Причина градации по типам — цена, а не важность.** Для типа A (живой чат-бот) полный цикл на каждую реплику стоит латентности и токенов при небольшой пользе для рутинных ответов, поэтому блок включается только для критичных ответов. Для типа C цикл дороже самой задачи. Это объяснение должно попасть в текст правила, иначе градация выглядит произвольной.

Цель — перенести этот паттерн в prompt-writer в двух местах:

1. **Процесс самого скилла**: prompt-writer пишет промпт через черновик, аудит и финал.
2. **Генерируемые промпты**: промпты, которые скилл выдает, сами содержат такой цикл для своих задач — с градацией по типам.

Решения, принятые на брейнсторме:

- Внедряем в оба места (не только в процесс скилла).
- Видимость: цикл идет внутренне, пользователь получает финальный промпт плюс 1-2 строки сводки аудита. Черновик и полные ответы аудита не показываются (детально — только если пользователь спросит).
- Invocation modes из humanizer — вне скоупа, осознанно игнорируем.

## Компонент 1: процесс скилла (SKILL.md, шаги 4-5)

Результат Шага 3 (заполненный шаблон) явно объявляется черновиком.

Шаг 4 переименовывается из «Прогнать чеклист» в «Аудит черновика» и состоит из трех действий:

1. Прогон черновика по `checklists/self-check.md`.
2. Два диагностических вопроса с краткими ответами:
   - «Какое master-правило этот черновик нарушает и где конкретно?»
   - «Что опытный промпт-инженер вычеркнул бы или переписал в первую очередь?»
3. Финальная версия, закрывающая все найденное.

Лазейка формального аудита закрывается явно (по правилу 17 самого скилла): ответ «нарушений нет» допустим только после конкретной проверки каждого пункта, а не как дефолтная отписка; хотя бы одно улучшение почти всегда находится.

Шаг 5: пользователю выдается финальный промпт и 1-2 строки сводки — что аудит нашел и что исправлено. Если аудит прошел чисто, сказать это одной строкой.

Оба workflow-сценария («новый промпт с нуля», «улучшить существующий промпт») обновляются: шаги self-check в них заменяются на цикл черновик → аудит → финал.

## Компонент 2: новое master-правило 19

Название (рабочее): «Встраивай цикл черновик → аудит → финал в генерируемые промпты».

Правило добавляется в конец списка master-правил с очередным свободным номером, чтобы не ломать существующие перекрестные ссылки. На момент написания спеки это номер 19; если раньше будет имплементирован план «Prompt Writer v2: Agentic task + Safety rules» (`docs/superpowers/plans/2026-08-08-prompt-writer-agentic-and-safety.md`), занимающий номера 19-21, правило этой спеки становится 22-м. Номер фиксируется в момент имплементации по факту содержимого SKILL.md; все упоминания «правило 19» в этой спеке читать как «новое правило цикла». Оно явно позиционируется как развитие правила 10 («Self-check вопросы перед критичными действиями»): правило 10 дает модели вопросы перед действием, правило 19 оформляет их в полный цикл с черновиком и ревизией. В тексте правила 19 — перекрестная ссылка на правило 10.

Градация по типам, прибитая явно (по правилу 18):

- **Тип D (extraction/transformation): обязательно.** Аудит-вопросы: соответствует ли результат методологии; нет ли в результате фактов, которых нет во входных данных.
- **Тип B (person imitation): обязательно.** Аудит-вопрос: «что в этом тексте выдает, что писал не [Имя]?».
- **Тип A (character assistant): только для критичных ответов** (эскалации, отказы, ответы с юридическими или репутационными последствиями). Полный цикл на каждую реплику чат-бота дорог по латентности.
- **Тип C (one-shot task): не встраивать.** Для одноразовой линейной задачи цикл — перегруз.

Правило пишется по канону скилла: reasoning внутри («почему»), без softening, с примером формулировки аудит-блока.

Quick reference в SKILL.md получает новый пункт про цикл.

## Мета-требования к имплементации

1. **Скилл применяется к самому себе.** Все новые тексты в SKILL.md, шаблонах и справочниках пишутся по правилам prompt-writer: decision-type заголовки, регистры модальности, reasoning внутри правил, закрытые лазейки, прибитая область применения, без softening и без капса вне hard limits.
2. **Синхронизация слоев** по CLAUDE.md: правило → выжимка в Master rules → Quick reference → full-rules.md → self-check.md → шаблоны. Ни один слой не остается рассинхронизированным.
3. **Без буквы ё** во всем русском тексте (конвенция репозитория).
4. Имплементация — в отдельном чате по плану, который будет написан после утверждения этой спеки.

## Вне скоупа

- Invocation modes (pasted/file/embedded) из humanizer — осознанно отброшены: два из трех режимов покрыты существующими workflow-сценариями, embedded-режим не нужен без планов вызывать prompt-writer из других агентов.
- Изменения routing, типологии промптов и остальных 18 правил — не трогаем.

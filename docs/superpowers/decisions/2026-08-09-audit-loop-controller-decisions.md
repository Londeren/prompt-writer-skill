## 2. Ruling по конфликту «один блок самопроверки против двух» (решение пользователя)

Бриф Task 5 Step 3 дает шаблону `character-frame.md` два блока (`<final_checks>` +
`<critical_answer_protocol>`), а тексты правила 22 (Task 3) и пункта чеклиста (Task 6)
запрещают два блока безоговорочно. Пользователь постановил: сузить формулировки правила
и чеклиста, шаблон оставить как в брифе.

**Следствие для Task 5:** `character-frame.md` делается ДОСЛОВНО по брифу, оба блока.

**Следствие для Task 3.** В тексте правила 22 предложение

> Цикл заменяет статичный self-check блок промпта, а не добавляется рядом с ним. Два блока самопроверки в одном промпте - это дублирование без выигрыша.

заменяется на

> Цикл заменяет статичный self-check блок промпта для того же класса ответов, а не добавляется рядом с ним. Два блока самопроверки для одного и того же класса ответов - дублирование без выигрыша. У типа A рутинные и критичные ответы - разные классы: `final_checks` для рутины и `critical_answer_protocol` для критичных сосуществуют, области обоих прибиты явно.

**Следствие для Task 6.** Пункт чеклиста

> - [ ] **В промпте один блок самопроверки, не два.** Цикл заменяет статичный self-check, а не соседствует с ним. Два блока проверки - дублирование без выигрыша.

заменяется на

> - [ ] **На один класс ответов - один блок самопроверки.** Цикл заменяет статичный self-check для того же класса, а не соседствует с ним. Исключение - выборочный цикл типа A: `final_checks` покрывает рутину, `critical_answer_protocol` критичные ответы, классы не пересекаются и область каждого прибита явно.

Причина, которую можно использовать в тексте: два блока покрывают непересекающиеся классы
ответов - это и есть градация по цене ошибки, которую правило 22 само вводит. Запрет был
сформулирован шире своего намерения, лечится правилом 18 самого скилла (прибить область
применения явно).

## 3. Общие констрейнты (из шапки плана, действуют всегда)

- Весь русский текст без буквы «ё».
- Стиль скилла: правило → «**Почему:**» → примеры. Без softening («желательно», «по возможности»,
  «постарайся»), без капса вне реальных hard limits, reasoning встроен в правило.
- Ничего не удалять из существующих правил и шаблонов кроме замен, явно описанных в брифе.
  Если правка требует изменить смысл существующего правила - остановиться и вернуть статус BLOCKED.
- Тексты вставок брать из брифа дословно, с поправками из разделов 1 и 2 этого файла.

## 4. Ruling по потерянным проверкам extraction-prompt.md (решение пользователя, fix round 1 Task 5)

Ревью Task 5 нашло: при замене `<final_self_check>` на `<draft_audit_final>` из шести старых
проверок в новый блок вобрались 4.5. Потеряны «Self-check каждого блока пройден?» и
«Все факты из входа учтены». Постановление пользователя — судьба у них разная:

**Пропуск фактов поднимается до третьего аудит-вопроса с презумпцией дефекта.** Возврат его в
хвост «Плюс проверить» в виде «все факты из входа учтены?» был бы регрессией, замаскированной
под починку: это бинарный вопрос с дефолтным ответом «да» — ровно та форма, которую таблица
«Работает / Не работает» правила 22 называет нерабочей. Для типа D пропуск не рутинная мелочь:
сама работа extraction — это полнота относительно входа. Фабрикация получила вопрос с
презумпцией дефекта, пропуск получает симметричный. Это же паттерн «тест работает в обе
стороны» (фабрикация = false positive, пропуск = false negative), который заложен в спеку
этапа 3 — закрыть сейчас дешевле, чем ловить повторно на ревью этапа 3.

**«Self-check каждого блока пройден» — рутина, ей место в хвосте «Плюс проверить».** Механическая
сверка не требует презумпции дефекта.

Синхронизация одним коммитом по трем слоям: `templates/extraction-prompt.md`, правило 22 в
`SKILL.md` (градация типа D + пример), раздел 4.17 в `reference/full-rules.md` (четвертая пара
в таблице «Работает / Не работает»). `checklists/self-check.md` не трогается — формулировка
«два-три диагностических вопроса» в 4.17 три вопроса уже допускает.

## 5. Ruling по регрессии в character-frame.md (решение пользователя, финальное ревью)

Финальное ревью нашло: `templates/character-frame.md:148` («Ассистент перед отправкой ответа
проверяет») не сужен, а `:170` («Остальные ответы ассистент пишет одним заходом с проверкой из
final_checks») уводит `final_checks` от критичных ответов. Итог — критичные ответы потеряли
проверки тона, anti-patterns, процедуры и границ, которые были у них на 290a76b.

**Решение: расширить аудит протокола (вариант 1).** У критичных ответов цена ошибки выше, значит
их проверка обязана быть надмножеством рутинной, а не подмножеством. Оставить как есть значило бы
осознанно закоммитить перевернутую пирамиду. Гонять критичный ответ через оба блока значило бы
сломать сужение правила 22 (два блока на один класс) без выигрыша.

**Механика расширения — зеркально решению §4 по extraction-prompt.** Тон, anti-patterns, процедура
и границы НЕ становятся третьим вопросом с презумпцией дефекта: они уходят в хвост аудит-шага
протокола, с явным перечислением, а не голой ссылкой на `final_checks` (правило 7: ссылка работает
слабее повторения, короткое перечисление — разумный компромисс). Презумпция дефекта остается у двух
осей с реальной ценой: нарушенное master-правило и обещанное сверх полномочий.

**Наблюдение в ledger, не для починки.** У аудита есть естественная тенденция пухнуть: в GREEN-прогоне
типа D аудит вырос до пяти пунктов при ориентире 4.17 «два-три диагностических вопроса». Там все пять
предметные, это нормально. Но паттерн отслеживать: длинный аудит превращается в формальность.
Механические пункты в будущих прогонах уводить в хвост «Плюс проверить», оставляя вопросами только
оси с презумпцией дефекта.
